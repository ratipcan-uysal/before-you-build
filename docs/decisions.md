# Decisions

Why this set is shaped the way it is. One entry per decision that had a real alternative — what was chosen, what was rejected, and why. Principles live in [`method.md`](method.md); this is the record of the calls made.

Kept in the repo rather than in anyone's head, because the most reliable reader of a decision record is the person who made the decision, six weeks later, about to make it again differently.

---

**Written from scratch, not adapted.** The set was distilled from a private toolkit that already worked. It was rewritten clean rather than sanitised, because that toolkit is soaked in one employer's context — real request documents, an internal API inventory, a question bank seeded from actual production incidents. Sanitising would have been faster and would have carried assumptions nobody could see any more.

**Skills in English, output in the user's language.** Turkish would have reached a real and underserved audience; English reaches more people and makes trigger matching more predictable, since descriptions are what the model matches against. One line per skill gets the second half back.

**One repo that is both plugin and marketplace.** `/plugin marketplace add` installs it in one step and updates automatically. A plain skills repo would be simpler to read and would push installation and updating onto the user.

**`SKILL.md` stays under 150 lines; detail lives in `references/`.** Lens catalogues, rubrics and output formats are read only when the phase that needs them is reached. Self-contained files would be easier to skim on GitHub and would pay their full cost on every trigger. CI enforces the limit, because it is the rule that erodes first.

**Grills are dialogic; producers are one-shot.** A grill asks one question and stops, because thinking happens in the pause. A producer that asked one question at a time would be abandoned halfway. `request-shaper` is the exception in both directions: it interviews, but in rounds of options rather than one open question, because it is extracting what the user already knows rather than making them think.

**Producing and grilling never share a skill, and never share a context.** A model that generates and then reviews approves its own work — from the ordinary pull of consistency, not vanity. This was proved during development: a design was generated from a brief and reviewed in the same session, and the brief's central decision had been violated in the drawing without the review catching it. `ux-grill` now declares the compromise when it applies.

**Silence scores zero.** In `readiness-score`, an item the document does not mention gets nothing; out of scope requires a quoted sentence. Partial credit for things a reasonable reader would assume is the single change that would make the score comfortable and worthless.

**`request-shaper` marks inferences `[ASSUMED]`; `readiness-score` caps a marked item at 1 of 3.** Without that contract the pair collude: one invents, the other scores the invention as content, and the user trusts a number built on nothing.

**Conditional items open on two axes, not one.** What the work does (transaction, data-display, input-collection, content-config, personalization) and where it runs (mobile-app, web, backend, multi-surface). A single work-type axis was tried first and put `backend-only` beside `transaction`, which is a category error — a backend change can perfectly well be transactional. Surface is also the axis documents leave implicit most often.

**`design-brief` decides and marks; it does not interview.** Two producing skills that both ask questions make the user answer twice. It drafts what it can, marks `[DECISION NEEDED]` with an owner for what it cannot, and hands over something a designer can start from.

**The design part is a loop.** `design-brief` → draw → `ux-grill` → back to `design-brief`. Some decisions cannot exist until something is drawn: "two recipients share a name, how does anyone tell them apart" is not derivable from a request. The second pass is usually the useful one.

**Tone is fixed: sharp but constructive.** Configurable intensity was considered and rejected — it adds mode handling to every skill and requires the harshest setting to be tested separately, for a preference most users would set once and forget.

**CI tests triggers and boundaries, not output quality.** **Fifteen skills** with adjacent descriptions fail by firing the wrong one, and the user never learns why the answer was off. Output-quality evals need fixtures that cost as much as the skills do; they wait until the set stops changing weekly.

**Verdicts come from a closed set with published definitions.** `READY / CONDITIONAL / NOT READY`, `SURVIVES / SURVIVES, NARROWED / UNRESOLVED / FATAL FLAW`. A summary drifts toward whoever spoke last; a label can be argued with.

**No confidence hedges.** Coverage is reported as fact — "27 items in scope, 6 with no evidence either way" — because "medium confidence" tells nobody what to do next.

**The draft contract goes as far as real operations, but only after asking.** The first version stopped at shape — what is asked for and what comes back, no verbs or paths — on the grounds that naming is where a contract conversation dies. That was too cautious: a shape-only document still leaves the concrete conversation to be had, and a wrong concrete proposal is corrected in five minutes while a vague one costs a meeting. So the concrete layer exists, gated on one question: which paradigm, which naming convention, how versioning works. Unanswered or mixed, it stops at shape and says why — a proposal in the wrong paradigm is worse than none, because it tells the reader the author does not know the stack. Asking rather than assuming is the same move `design-brief` makes with design tokens, which it never invents.

**`api-needs` will propose a draft contract, which crosses the set's own line.** Everywhere else the rule is what and why, never how — naming endpoints and field shapes is designing, and designing the backend belongs to the people who own it. The exception is deliberate: a product manager who arrives with only a list of needs is negotiating from a weaker position than one who arrives with something concrete to argue against. The risk is that an experienced backend team reads a proposed contract as overreach, so the need must stand on its own and the draft must be a separate section that can be deleted without losing anything.

**API needs are derived from the flow, not from the screens.** Screens tell you about reads. Flows tell you about writes, sequencing and failure — which is where the hard questions live: what has to be atomic, what can be retried, what happens when step four succeeds and step five does not. Deriving from `design-brief` alone was the original plan and would have produced a read-shaped view of the problem.

**Output follows the user's language; markers do not.** Prose adapts, but `[ASSUMED]`, `[DECISION NEEDED]`, `[DRAFT]`, `READY`, `Critical`, `reads`, `acts` and every other status token stay in English. This reverses an earlier call to translate everything, and the reason is mechanical rather than stylistic: markers are consumed downstream — `readiness-score` caps an item because it matched `[ASSUMED]`, `api-needs` reads the touchpoint marks `flow-map` wrote. A translated marker is a broken contract that fails silently, and it makes one finding look like two different things across two documents. It also matches how the vocabulary is already used in practice: a term whose translation reads worse is left in English.

**CI reads the prose, not just the skills.** Removing `state-matrix` swept `skills/` and `evals/` and missed a public example, and the dead pointer passed CI because CI had never opened `examples/`. The validator now resolves every relative link in the repo and checks every backticked kebab-case term in prose against the skills that exist plus a declared vocabulary list — seven terms, all of them axis values the skills define. The alternative was a list of retired names, which is cheaper and only ever catches removals someone remembered to record; the vocabulary list catches renames and typos too, and costs one line when a genuinely new term is coined. Being made to add that line is the check working, not friction.

`examples/` and `commands/` are live surfaces: a retired name there is an error with no exception, because a worked example that describes a skill nobody has is worse than no example. `docs/` and `README.md` may name one when the reason sits in the same paragraph or the one before it — a decision record has to be able to record what was removed. `CHANGELOG.md` is exempt outright, since every entry already sits under the version it was true at.

Three defects turned up the first time it ran, all in the most-read documents: a loop diagram still routing through the removed skill, and `method.md` describing itself as eight principles when a ninth had been added to it.

**`state-matrix` was removed at v3.0.** The probation below was written before the condition was met, and then two arguments for keeping it failed under their own test. The granularity claim was wrong: `risk-interrogate`'s rule that every question must name something in the material already forces surface-level specificity, and its own worked example is a surface-level question about this same feature. The producer-must-not-sweep argument defended separation from `design-brief`, not existence — the work moved to `ux-grill`, which is a checker, so the principle holds. What remained was one finding the others would plausibly have reached, against the standing cost of a boundary that must be defended, tested and kept from drifting. The per-surface sweep is now `ux-grill`'s states lens; the project-wide constraints are `design-brief`'s.

**`state-matrix` stays separate from `design-brief`, and is on probation.** Two rounds of narrowing took the project-wide constraints out of it and banned rows phrased as checks, which left the thinnest skill in the set: conditions a surface's own dependencies create. Folding it into `design-brief` was considered and rejected — the brief is the producer, and a producer that also sweeps is checking its own decisions, which is the failure this set is built against. It survives because the granularity is the point: `risk-interrogate` answers at feature level and nobody can draw "data integrity", while "the threshold never arrived" is a screen. If a real run puts its overlap with `risk-interrogate` above half, merge them.

---

**The set serves two builders, and the second one needs it more.** One writes a request and hands it to a team. The other hands it to a model that writes the whole product — app, web and backend. The original framing was the first, and it produced a chain that ends at *ready to build* and stops. That is a defensible end for a team, who ask when something is missing. It is the wrong end for a generator, which fills every gap silently and confidently and returns something that reads as finished. The pattern was already in the set before the audience was: `design-brief`'s third phase is called *draft what a generator would otherwise invent*. What changed is reach — the same treatment now has to cover the parts of a product that are not screens.

**The line is not what against how.** The old rule was *what and why, never how*, with `api-needs`'s draft contract recorded as a deliberate exception. That rule was aimed at a team's autonomy: naming endpoints for the people who own the system is overreach. Against a generator there is no autonomy to protect — withholding a decision does not leave it open, it hands it to whoever is generating, who settles it in a second and never mentions it. The axis that holds for both readers is **what the builder must not invent** against **what the builder does better than us**. Entities, identity rules, states, copy, prohibitions and acceptance are the first. Architecture, file layout, library choice, types, indexes and migrations are the second, and putting those in a product document is still how the document gets dismissed whole.

**`data-model` names the nouns, and runs before `api-needs`.** A schema is a stack of product decisions wearing storage clothes: copy a name onto a record and history holds, reference it and a rename edits the past. Both work, both survive review, and nothing in the code records which was chosen. `api-needs` was the nearest existing skill and does not cover it — a contract says what the system provides, not what it remembers, and its draft was being written over nouns nobody had defined. The order between them was arguable, since both feed off `flow-map`'s touchpoint marks; the tiebreak is that a wrong entity model corrupts every endpoint while a wrong endpoint list leaves the entity model intact. Its first run on a real flow returned four mismatches against the flow it was derived from, and one defect in itself: a sweep rule that contradicted `flow-map`'s own definition of `acts`.

**`design-brief` stays ahead of `flow-map`, and the threshold was set before the measurement.** The chain's own README drew flow before design while the worked examples ran design before flow, so one of the two was wrong. The test declared in advance: match every `ux-grill` finding that names a closing decision against the mapped flow, and swap the order if more than half would have been answered there first. Result — **5 of 12 fully, 3 partially, 4 not at all.** Below the line, so the order held. The useful part was not the number but the sorting: every finding the flow would have caught was an error path and its exit, and every one it would not was identity, placement, contrast or notation. So the fix is not a swap but a dependency — `design-brief` now names the error paths it needs and says plainly that running `flow-map` first will change what it produces. Swapping was rejected because the design loop depends on something being drawn early; a flow mapped over an undesigned feature produces steps with no surfaces.

**`slice` goes fourth, not last.** It was first placed at the end, next to the handoff, which is where scope-cutting usually appears on a diagram and where it is useless. Running the chain across the full scope and cutting afterwards means the design, the flow and the contract were produced for things that will not ship — which is exactly what happened in the worked example, where a brief and a flow were written for a web surface the request itself defers. The cut comes straight after the request is defined and measured, and everything downstream runs on the first slice only.

**`slice` and `build-context` are named in the chain before they are written.** A planned skill in the README's diagram and in this file is a commitment that can be checked; a planned skill inside a `SKILL.md`, a worked example or the router would be a promise to a user who cannot run it. The validator enforces exactly that split, the same way it does for skills that have been removed.

**A new skill is written against the problem it solves, not against the set it joins — so CI checks the joining.** Five instances, and the last three landed on the same day the earlier two were being audited: `api-needs` shipped without the `emits` contract `flow-map` declares; `decision-memo` shipped named by no skill and went unrun for weeks as a result; `data-model` shipped with a sweep rule contradicting `flow-map`'s own definition of `acts`; `build-context` shipped without the self-review guard every other checker carries; `prior-art` shipped without saying where its output goes.

A written checklist was the obvious answer and it is the answer that failed — three of those five happened after the pattern was already understood. What actually caught things, all day, was the validator, because it is the only part of this that runs whether or not anyone remembers it. So the three joinable properties that can be checked mechanically now are: **every skill is named by another skill** (nothing routes to it otherwise, which is exactly how `decision-memo` sat unused), **every marker a skill emits is covered by its own Language rule** (a translated token breaks a contract silently), and **every skill states a boundary**.

What cannot be checked is whether both ends of a declared contract are actually implemented, or whether a producer carries the guards its siblings carry. Those were found by running the skill on real material and by being asked *"is this clear?"* — which is the standing rule this entry also records: **a skill is not finished when it is written, it is finished when it has been run once on real input and one other skill has been checked against it.**

---

**A finding raised after a document is written goes back through the skill that wrote it, in a new version.** The alternatives were a re-score and letting the pack collect everything. Re-scoring is wrong at the root: `readiness-score` measures, it does not carry — a finding handed to it becomes a lower number and stays outside the document. Letting `build-context` collect them is the status quo, and the status quo is what failed: on a full chain run `prior-art`'s three most decision-changing findings surfaced ten documents late, by which point the flow, the model and the contract had all been written over the unamended request. So `request-shaper` gets a second pass, which is not a new mechanism but the one the design loop already runs — a brief is grilled and the record comes back as v2. The producer of the finding cannot do this: every grill in the set is forbidden from rewriting, and that separation is why the findings are worth reading. What was missing was never the finding or its recipient — both were written down. It was the **named writer**, and a departure handed back without one dies where it was raised.

**A producing skill and the skill that checks it are never trusted in the same session without a declared guard.** `flow-grill`, `ux-grill` and `build-context` carried it; `readiness-score` did not, which is backwards — `request-shaper` → `readiness-score` is the pair that actually runs back to back, and it is the one case where the output is a number, so it reads as measurement whoever produced it. The guard cannot be checked mechanically, so it is a rule here: any skill that assesses another's output states, before its verdict, whether the same session produced what it is assessing. The mechanical half is already enforced — every skill states a boundary — and this is the half that is not.

**A question raised before the document exists must have a named carrier.** `idea-grill` in proxy mode produces questions for the requester; nothing was told to carry them. On a measured run the first question asked — whether the requested thing was the right response to the problem at all — appeared in none of the fifteen documents that followed, and only the final pack noticed, last. It was not answered, not ruled out of scope, and not disputed. It was dropped, and the ones dropped this way are always the earliest, which is to say the ones about whether to build the thing. `request-shaper` now takes in whatever list arrived with the material and reports how many. The general form: a skill that runs **before** the document exists must name the document that will hold its output, and a skill that runs **after** it must name the pass that writes it in.

**Read this file before changing the chain's order, including in the router.** Within an hour of the run above, a router row was written telling users to map the flow before writing the brief — from the same evidence the order test had already weighed, and reaching the opposite conclusion to the one recorded four entries up. It would have reversed a call made against a threshold declared in advance, and nothing in the repo would have flagged it: the validator checks that a skill is named, never that a claim about sequence matches the decision that set it. Fresh evidence is how the order should change; it is not how it should change silently.

**A cut is a change to the request, and it travels the same way every other late finding does.** `slice` produces quotable exclusions so that `readiness-score` can mark items out of scope, and that mechanism was only half built: the exclusions existed and nothing rewrote the request's open list, so every document downstream kept counting blockers that belonged to parts already removed — four of fourteen on a measured run. The fix is not a new mechanism but the one already there: `slice` is a source for `request-shaper`'s second pass, like `prior-art` and `impact-radar`. What it needed was a third outcome, because an item that left scope is not an item that closed. Written as closed it vanishes and returns unanswered with the deferred work; left open it blocks a release nobody is building. It goes to its own list under the exclusion that retired it, quoted, and it stays retired only as long as that exclusion holds.

**Scope grows downstream of the cut, and it grows through good reasoning.** A brief decided a screen needed a comparison figure the slice did not contain; the model stored what that implied; the contract returned it; a risk pass then asked a question premised on it being shown. Four documents, each step following from the last, none of them following from the thing somebody approved — and the addition is invisible precisely because every individual step is correct. The rule is placed in the three skills that make additions rather than centralised in `slice` or left to `build-context`, and that is deliberate: the producer is where the addition happens and the only place it can be marked as one; `build-context` finding it is four documents too late, which is exactly how it was found. Repetition across skills is the same trade the Language rule already makes — three copies that fire at the right moment beat one copy nobody reads at the wrong one. **Nobody is forbidden from adding. They are forbidden from adding silently.**

**The self-review guard was a confession, and it is now a delegation.** Four skills carried it and all four discharged it the same way: declare the review compromised and recommend a clean-context repeat. Nothing performed the repeat. Measured across two full chain runs: fifteen compromised reviews, zero repeats — because the recommendation is addressed to a user who would have to open a new session and re-attach the documents, and nobody does that at the end of a long session. Both published worked examples open with the confession.

So the grills now hand the pass to a subagent whose entire input is the artefact's **file paths** and the skill's own instructions. That is the condition principle 7 actually asks for: a reviewer who did not produce the thing. Paths rather than pasted content, because pasting re-imports the framing the guard exists to remove; the verdict is reported as the subagent's and is not softened; and where the material came from outside the session, none of it applies and the review happens inline. The confession survives as the fallback for when no subagent is available, which is the only honest place for it.

The guard also reached three skills that assess another's output and never carried it — `risk-interrogate`, `prior-art` and `impact-radar` — which `docs/decisions.md` had required since the rule was written and nothing had checked. It is checked now: a skill that carries the guard and has lost the delegation sentence fails CI, because seven hand-copied paragraphs drift, and the drift back is exactly to the version that never worked.

**And the chain diagram is now checked against the skills.** It sits in a fenced block, and `strip_fences` blanks every fence before the prose checks run — so the most-read map in the repo was the one document CI could not see, and it had drifted: a `flow-grill → data-model` edge that contradicted this file's own rule that `data-model` and `api-needs` both feed off `flow-map`'s touchpoint marks, plus two edges no skill implemented. The check reads that one block deliberately: a skill name in a fence is quoted content everywhere else in the repo and a claim about the set here.

**The READY threshold has never been shown reachable, and the first attempt says the rubric is why.** Four scorings across two worked examples returned 12, 39, 25 and 25 — all `NOT READY` — and both packs returned `ASK FIRST`. A set that has never published a pass is indistinguishable from one that cannot pass anything, so a third example was run on a small, genuinely well-prepared request. It scored **62, `CONDITIONAL`**, with no blocker firing, and part of the gap is not thinness: `readiness-score` asks a read-only render component about data residency, running cost, end-to-end traceability and go-live sign-off, and it earns zero on all of them. **The size of that part was published wrong and is corrected here.** The first write-up put it at eighteen points and claimed four exempting sentences would reach the high seventies; recomputed from the scoring's own items, four exemptions give **64.3**, every zero-scored item in the rubric gives **77.1**, and the largest single shortfall is **K3 at 9.38** — behaviour and rules, which is the request's own. The unavoidable tax is about **twelve points**, not eighteen.

Two readings, and the difference decides whether anything changes. Either the request should have exempted those items with one quoted sentence each — which the evidence gate already permits and the requester simply did not think to write — or the threshold is calibrated for `transaction` work and is the wrong bar everywhere else. **Neither is established by this**, and the arithmetic above is why the first reading was overstated when it was written. Nothing is being changed on one instance. The next `capability` or `content-config` run tests it, and if that one also cannot exempt its way past 70 while being genuinely ready, the weights are the problem rather than the writing.

Recording it rather than acting on it is the point. Moving a threshold so that an example passes is the same failure as writing an example that passes: it makes the number agree with the story instead of the other way round.

**A sixteenth skill, and why it is not being added yet.** In both full chain runs `readiness-score` scored the success criterion 0, `slice`'s signal test failed, and `api-needs` named the event need — and no skill in the set produces the thing. `request-shaper` asks and accepts "not discussed"; nobody defines the baseline, the target and the comparison that would show the work succeeded. That is the strongest case for an addition since `build-context`, and it runs against a published position: fifteen skills, none planned.

The kill condition, declared in advance the way `state-matrix`'s was before it was removed at v3.0: **if a third full run also ends with the success criterion undefined and no skill able to produce it, the case is made on three instances and the skill is written.** If a run reaches a defined success criterion through `request-shaper` alone, the gap was an interview problem and the candidate dies here. The third example run at 4.4.0 does not count as that test — its success measure arrived written in the request, which answers nothing about whether the set can produce one.

**Versioning, written down because three bumps were made without a rule.** The repo has a version in three places and CI now keeps them equal; what it did not have was a statement of when to move which number, so each release was an author's reading of what a minor meant. The rule, matching what the history already did: **a skill added or removed is a major**, because a chain with a different set of skills is a different set. **A skill's contract changing is a minor** — a new rule it must follow, a new handoff, a new check that fails work which used to pass, a new worked example. **A correction that changes no behaviour is a patch.** Where a change makes the same document score differently, the entry says so under *Heads up*, which it already did before there was a rule for the number above it.


**The success-criterion kill condition has fired, and the skill is still not being written.** The rule declared above was: if a third full run also ends with the success criterion undefined and no skill able to produce it, the case is made on three instances. The bank run is that third instance and it did end there — `readiness-score` scored the criterion 1 rather than 0, and only because the committee named a monthly count. What the run showed is sharper than the gap the candidate was drawn against: the metric exists, it is reported to the body that ordered the work, and it **cannot distinguish a control that worked from one that was bypassed**. Nobody in the chain could produce a better one, but nobody needed a new skill to see it either — `idea-grill` cracked it in round one and `prior-art` found the regulator who publishes the same objection.

So the fix went into the rubric rather than into a sixteenth skill: a success criterion that cannot tell the thing working from the thing being bypassed now scores as absent, which fires the blocker the old reading missed. **The candidate stays open with a narrower condition.** The gap it was drawn against was "no skill produces a success criterion"; what three runs actually show is that the criterion is usually *stated and wrong*, which is a scoring problem and now has a scoring answer. It gets written only if a run produces a criterion that survives the new rule and still cannot be acted on.

**Two independent sessions inventing the same patch is the threshold for writing it into the skill.** `api-needs` and `build-context` ran in separate clean contexts on the bank chain, neither seeing the other's output, and both hit the same missing rule — what to do when the document you derive from has already failed an audit that nobody acted on — and both wrote their own version of it into their output and declared it. Neither was wrong. That is the signal the set was missing a sentence, and it is a cheaper signal than three runs, because it does not depend on the same reader noticing twice. The standing rule: **when two passes that could not have coordinated invent the same rule, it goes in the file.**

**Principle 11, and why it is a principle rather than eight edits.** Eight skills carried a rule that hands a decision to a user, and the set is mostly run unattended. Fixing the eight would have left the ninth to be written the same way. The measured cost is what makes it a principle: on this chain, whether roughly forty unanswerable items became open questions or capped `[ASSUMED]` lines — a difference that moves the score without moving what anybody knows — was decided by a rule that had delegated it to nobody, and the document that took the default never said it had. CI now checks that a rule requiring an answer says what happens when none comes; the check found three cases the release had already missed.

**A table was the wrong container, and it was measurable before anyone read a document.** Every output spec in the set reaches for a table, and none of them said how much a cell may hold. Across the published examples that produced an 84-word cell and a 748-character row: a shape that is scannable in the spec and unreadable in the artefact. The fix is not shorter findings, which would cut real content to fit a grid. It is a one-line index for scanning and a labelled block for the reasoning, plus an identifier so the two halves point at each other and a later document can cite `F3` instead of quoting a paragraph back.

Identifiers stop at entities. Numbering them would put `E1` next to a flow that already writes `E4` and `EA2`, and an ambiguous citation is worse than a longer one. An entity has a name, and the name is the identifier.

**The prose of a rewrite gets measured too.** The new spec text ran at 22.2 em dashes per 1000 words against the repo's own 12.7, which is the house voice drifting rather than following. Restructuring the sentences that carried them brought it to 11.9, and mean sentence length from 23.1 words to 19.2. The measurement is [slop-check](https://github.com/ratipcan-uysal/slop-check), a separate tool and not a dependency of this plugin. Nothing here calls it and the skills do not require it.
